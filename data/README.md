# Data

| File | What it is |
|---|---|
| [`Sajid_Procurement_Integration_Synthetic_Data_Expanded.xlsx`](Sajid_Procurement_Integration_Synthetic_Data_Expanded.xlsx) | The client's synthetic data pack, unchanged. **The default data set** for the services, the demo and the workbook tests. |
| [`employee-directory.json`](employee-directory.json) | Who raised which workbook requisition and what each employee may do through the assistant. **Our assumption**, because the workbook does not say (see below). Generated by [`scripts/generate_employee_directory.py`](../scripts/generate_employee_directory.py). |

Both are read directly by the services (`Procurement.SyntheticData`, using Microsoft's Open XML SDK) and copied next to every build, so nothing has to be imported into a database first. A second, generated data set (250 requisitions, seed 42) is kept for stress and edge-case tests; see [Data sets](#data-sets).

## How each sheet is used

| Sheet | Rows | Used by | How |
|---|---:|---|---|
| `Approved_Requisitions` + `Requisition_Lines` | 120 + 200 | Source mock | Served as the source system's requisitions, in workbook order, 40 per page. Nothing is corrected: blank dates and zero totals reach the integration as they are. |
| `Failure_Injection` | 78 | SAP mock | `DUPLICATE`: the document already exists in SAP. `RATE_LIMIT` / `TRANSIENT_5XX`: the first *Trigger_Attempts* creates get `429` (with `Retry-After`) or `503`. `VERSION_CONFLICT`: a create carrying an older version than *Remote_Current_Version* gets `409`. `VALIDATION`: nothing to inject; the integration catches these before sending. |
| `Mock_Remote_Status` | 65 | SAP mock, tests | The SAP document number for each requisition (`MOCK-SAP-5xxxx`), and its expected status and version. |
| `Quarantine_Expected` | 50 | Tests | Each requisition must be quarantined with the matching reason and field (W02). |
| `Reconciliation_Expected` | 120 | Tests, `procsync check-expected` | The first run's per-requisition report must match on result, SAP document, attempts, failure category and source version (W01). |
| `AI_API_Contract_Tests` | 60 | Tests | Each row is executed against the Assistant API and must return the expected status (W07). |
| `Mock_Suppliers` | 50 | — | Read, but not used: no requisition or line refers to a supplier. |

## Mapping to our model

| Workbook | Our model / SAP mock |
|---|---|
| `Approval_Status` `Approved` / `Pending` | `Approved` / `PendingApproval` (pending ones are skipped) |
| `Requester_Dept`, `Business_Purpose` | `department`, `justification` |
| `Required_By` (blank = missing) | `neededBy` (missing → `MissingRequiredField`, i.e. `REQUIRED_DATE_MISSING`) |
| `Total_Amount` ≤ 0 | `AmountNotPositive` (i.e. `AMOUNT_NOT_POSITIVE`), reported before any line-total mismatch |
| `Item_Code`, `Unit`, `Unit_Price_QAR`, `Tax_Code`, `Cost_Centre` | `materialCode`, `uom`, `unitPrice`, `taxCode`, `costCenter` |
| `Remote_Status` `Created` / `Approved` | SAP release status `""` (not yet in release) / `02` (released) |
| `Processing_Result` `Duplicate` | Already in SAP; the existing document is linked and nothing is created |

## Assumptions, and questions for the client

The workbook leaves a few things open. These are the choices we made; each is easy to change.

1. **Company code and plant.** The workbook has neither, but SAP needs both. Every requisition belongs to one synthetic Qatar entity: company code `3000`, plant `3100`.
2. **Who owns which requisition.** `AI_API_Contract_Tests` uses employees `E1001`–`E1060` and the rule "own record or delegated procurement role", but nothing links employees to requisitions or roles. [`employee-directory.json`](employee-directory.json) assumes that employee `E10NN` raised `REQ-70NN`. The five status reads that expect `403` (`REQ-7001`, `7015`, `7029`, `7043`, `7057`) were raised by a colleague in the same department. The four creates that expect `403` come from employees who may read but not raise requisitions. `E1900` holds the delegated procurement role.
3. **What a version conflict is.** The workbook has the remote reject version 2 because it knows version 3. We read this as: the requisition was edited in the source while it was being sent. The source mock's list endpoint still shows the earlier version (as a lagging read replica would), while reading the record itself returns the new one. The integration re-reads the record and sends it once more, as the expected behaviour says.
4. **A zero total with non-zero lines.** `REQ-7071` has a total of 0 while its lines add up to 25,452. We report "total must be greater than zero", as the workbook expects, rather than "total does not match the lines".
5. **Suppliers.** No requisition refers to a supplier, so the four inactive suppliers cannot affect anything. Should requisition lines carry a supplier?
6. **`403` for someone else's requisition.** The workbook expects `403`. We follow it, although `404` would avoid confirming that the requisition exists.

## Data sets

The source mock, SAP mock and Assistant API all read `Dataset:Source` from configuration:

| Value | Source | SAP | Used by |
|---|---|---|---|
| `Workbook` (default) | The client's 120 requisitions | Seven pre-existing documents, the workbook's failure schedule and document numbers; a create for an existing reference is answered with `409` | `run-all`, the demo, tests W01–W07 |
| `Generated` | 250 requisitions from seed 42, with 23 deliberate defects | Empty; duplicates allowed, like real SAP | Scenario tests S01–S22, A01–A10, mock tests, the chaos sample |

Switch at runtime with `POST /_admin/reset?dataset=Workbook|Generated` on each mock. The Assistant API's catalogue follows its own setting (workbook items and cost centres, or the generated catalogue).
